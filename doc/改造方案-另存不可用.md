## 实现方式

把单文件拆成“壳 + 外部资源”，并用绝对路径制造线上/线下差异：

```
index.html                 壳：介绍文案 + DOM 骨架 + 两个相对引用
assets/style-a1b2c3.css    原全部 CSS
assets/app-a1b2c3.js       原全部 JS（<script type="module"> 引入）
assets/core-a1b2c3.js      核心 SVG 生成函数（独立 ES module）
```

关键设计：

1. `<main>` 默认 `display:none`，由 app.js 启动时显示。无 JS 时只剩介绍文字。
2. HTML 用 `type="module"` 加载 app —— 浏览器另存后以 `file://` 打开会被 CORS 阻断，界面不启动。
3. 核心函数（`buildSvg`、`buildOneSvg`、`lineElements`）抽到 `core-*.js`，主脚本用**绝对路径** `import('/assets/core-a1b2c3.js')` 加载。
4. 线上部署时该路径正好指向真实文件 → 功能完整；完整另存后资源被浏览器放进 `xxx_files/`，而 JS 内的绝对路径不会被改写 → 本地服务器返回 404 → 生成功能失效。这与 SVGlo 的 wasm 失效机制完全一致。
5. `pathD` 保留在 app.js（供实时曲线预览使用），通过参数传给 core，避免 core 加载失败时连取点预览都崩溃。

## 需要安装的 package

**无。** 纯文本拆分与手工命名即可，不需要 npm/Vite/esbuild。若后续想自动化打包与 hash 命名，可选 esbuild，但当前不必。

## 代价

1. 本地使用必须通过 HTTP 服务访问（如 `python -m http.server 8000`），不能双击 `index.html`。这是达到“另存不可用”的必然代价。
2. `file://` 下已有的 localStorage 数据不会迁移到 `http://localhost`，刷新后需重新取点。
3. 维护变为 4 个文件，但 HTML 壳稳定，日常只改 `app-*.js` 与 `core-*.js`。

## 验证方法

- 在 `pic2svg` 起服务器访问 → 取点、生成、下载全部正常。
- 模拟完整另存（资源移入 `_files/`、HTML 引用改相对）→ 确认界面出现但生成按钮失效。
